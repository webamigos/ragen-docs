The Ragen CLI puts a `ragen` command on your `PATH`. It scaffolds an installation, moves documents in and out of its knowledge base, and searches it — and it grows toward managing an installation end to end, signing in and checking its health included, without leaving your terminal.

```bash
npm install -g ragen-cli
ragen --help
```

<Note>
  The package is `ragen-cli`; the command is `ragen`. npm declines the plain name because its similarity filter reads it as too close to existing packages, so the install line differs from what you type afterwards.
</Note>

## Requirements

The CLI asks for **Node.js 20 or newer**, which is deliberately lower than the **Node.js 24** a Ragen installation itself needs. This is a client — refusing to print help on an older runtime would be needlessly strict. `ragen create` still enforces the real requirement at the point where an older Node would damage the install.

## What it does today

| Command | What it does |
|---|---|
| `ragen create [dir]` | Scaffolds a self-hosted Ragen installation |
| `ragen kb <command>` | Lists, uploads, checks and deletes knowledge base files — `ls`, `upload`, `status`, `rm`. Since 0.3.0 |
| `ragen search <query>` | Prints the passages chat would answer from, without generating an answer. Since 0.3.0 |
| `ragen login` | Checks an API key against an installation and saves it with the API address. Since 0.3.0 |
| `ragen logout` | Forgets the saved address and key. Since 0.3.0 |
| `ragen doctor` | Checks that this terminal can reach an installation and use its key. Since 0.3.0 |
| `ragen brain <command>` | Reads [Ragen Brain](/concepts/brain#from-the-terminal) through the public API — `next`, `doctor`, `findings`, `pages`, `graph`, `query`, `export`. Needs `RAGEN_API_URL` and the API key of an owner or admin in `RAGEN_API_KEY` (or `--url` and `--api-key`). Since 0.2.0 |
| `ragen help` | Lists every command, built or not |
| `ragen version` | Prints the version of the CLI |

`ragen create` hands the work to [`create-ragen-app`](/quickstart) and forwards your arguments unchanged, so these two are equivalent:

```bash
npx create-ragen-app my-ragen-app --skip-docker
ragen create my-ragen-app --skip-docker
```

<Tip>
  The scaffolder's flags — `--yes`, `--provider=`, `--skip-docker`, `--skip-install`, `--ref=` — all work through `ragen create`. The [Quick Start](/quickstart) documents what each one changes.
</Tip>

The scaffolder stays a separate package on purpose. It is the only thing exercising the first-run path, it is tested on every change to the repository, and a second copy of that wizard inside the CLI would drift out of step without anything noticing.

## Connect to an installation

Every command except `create` talks to an installation's [public API](/api-reference/quickstart). Create an API key under **Organization** → **API keys**, then save it once:

```bash
ragen login --url https://api.example.com
```

`ragen login` asks for the key without echoing it, checks it against the installation, and saves the address and key only if the key is accepted. You can also pipe the key in, which suits a CI job:

```bash
echo "$RAGEN_API_KEY" | ragen login --url https://api.example.com
```

<Warning>
  The key is saved as plain text in `~/.config/ragen/config.json` (`$XDG_CONFIG_HOME/ragen/` when that is set, `%APPDATA%\ragen\` on Windows), readable only by your user. Run `ragen logout` to delete it. Prefer the hidden prompt or a pipe to `--api-key`, which lands in your shell history.
</Warning>

Environment variables take precedence over the saved connection, and `--url` and `--api-key` take precedence over both:

```bash
export RAGEN_API_URL=https://api.example.com
export RAGEN_API_KEY=sk-...
```

### Check the connection

```bash
ragen doctor
```

```
ok    node       v24.15.0
ok    cli        ragen-cli 0.3.0
ok    url        https://api.example.com (from ~/.config/ragen/config.json)
ok    key        sk-749…sgF8 (from RAGEN_API_KEY)
ok    api        answers
ok    auth       the key is accepted
ok    models     gpt-oss-120b, mistral-small-3.2
-     brain      off for the organization, or the key's user is not an owner or admin
```

`ragen doctor` shows which address and key are in use and where each one came from, which is usually what is wrong when commands disagree. It tells "nothing answers at this address" — including the panel's address given in place of the API's — apart from "the key was refused", and warns when a newer CLI is on npm. It exits with a non-zero code when a check fails.

<Note>
  `ragen doctor` checks this client's path to an installation. Whether the installation itself is configured well — its environment, model routes and queue — is checked on the host, where the setup page and `npm run gateway:preflight` report it.
</Note>

## Upload and manage documents

`ragen kb` works on the knowledge base's files through [`/v1/files`](/api-reference/files):

```bash
ragen kb ls                          # the newest 20 files
ragen kb upload docs/*.pdf --wait    # upload, then wait until each one is indexed
ragen kb status file-abc123          # uploaded, processed or error
ragen kb rm file-abc123              # delete a file and its chunks
```

| Subcommand | Options |
|---|---|
| `ls` | `--limit <n>` for a different page size, `--all` for every file |
| `upload <file...>` | `--wait` to wait until indexed, `--timeout <seconds>` (default 600) |
| `status <file-id...>` | `--wait`, `--timeout <seconds>` |
| `rm <file-id...>` | — |

Every subcommand accepts `--json` to print the API's response instead of a table.

<Note>
  **The API key decides where files go.** A key scoped to the whole knowledge base uploads to and lists the files that belong to no assistant. A key scoped to an assistant works on that assistant's files. The CLI has no option for this — it would only be able to disagree with the server.
</Note>

`upload` takes files, not directories. Let your shell expand a pattern such as `docs/*.pdf`.

### Use it in a script

Both `upload --wait` and `status` exit with a non-zero code when a file fails to index. `--wait` also exits non-zero when a file is still indexing at the timeout, and prints the `ragen kb status` command to check it later.

```bash
ragen kb upload handbook.pdf policies/*.md --wait || exit 1
```

Uploads are rate limited per minute. When a batch reaches the limit, the CLI waits as long as the server asks and carries on — you see `Rate limited; waiting 60s before note-11.md.` — instead of failing the rest. While waiting for indexing it checks all files in a single request every few seconds, so a large batch does not use up the limit by itself.

## Search the knowledge base

```bash
ragen search "How many days do customers have to return a mug?"
```

`ragen search` calls [`/v1/search`](/api-reference/search). It prints the same PII-redacted context block that the chat endpoint passes to its model, followed by the files it came from. When an answer in chat looks wrong, this shows whether retrieval found the right passage or the model ignored it.

| Option | What it does |
|---|---|
| `--max <n>` | At most `n` passages, 1–20. The default is your organization's retrieval setting |
| `--assistant <id>` | Search one assistant's files; also read from `RAGEN_ASSISTANT_ID`. The API key must allow it |
| `--json` | Print `context` and `file_ids` as JSON |

## What is coming

These commands are listed in `ragen help` under **Not built yet**:

| Command | What it will do |
|---|---|
| `ragen plugin` | Manage custom MCP connectors |

<Warning>
  A command that is not built prints what it is waiting on and **exits non-zero**. That is deliberate: a script that runs `ragen plugin install` against a version that cannot do it should fail, not read the silence as success.
</Warning>

`ragen plugin` is the furthest out, and it waits on something larger than the CLI. Ragen's extension API is MCP — third-party code runs in its own process and never inside the application — and the piece that lets you point Ragen at a server of your own is designed but not yet built. Until then, see [MCP connectors](/integrations/mcp-connectors) for the connectors that ship today.

## Versioning

The CLI talks to an installation over the [public API](/api-reference/quickstart), and self-hosted deployments run many versions at once. Its version number describes the client, not the server you point it at. Upgrade it like any other global package:

```bash
npm install -g ragen-cli@latest
```
